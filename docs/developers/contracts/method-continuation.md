# Method continuation

Ordinary construction supply, frame completion and roof building are native work. A previously
installed exact commitment preserves a running task but does not start another
Supply, FinishFrame or BuildRoof at its next observed boundary. It releases the participant;
if another participant depends on its remaining work, the attempt ends and releases
its exact owners. This supplies no completion evidence or material refund, and
leaves an unrelated running participant unchanged.

Standing Deconstruct (without roof prerequisites), Uninstall, CutPlant,
RemoveFloor and Mine designations follow the same boundary handback. Their
existing `removal-` task identity distinguishes this producer from planned
footprint clearance, which has not yet created native work. Generation and
binding share that identity prefix; neither invents completion from handback.
Planned preplacement clearance, roof-prerequisite demolition and custom haul-out
remain explicit pending their native-work migration.

An actual native job takeover detaches the old execution handle. The existing
pawn-fact invalidation wakes the worker, which re-reads all Method participants.
A positively absent or different owner ends that coordinated attempt: remaining
exact owners are released with their observed assignment revisions; the new owner
is never released. Missing participant observations defer cleanup. The journal
retains the attempted Method as history, with no stale task restart, food credit
or refund of partial work and carried inputs. Fresh observations govern recovery.

For a finite `OrderedWork` intervention, a terminal dispatch receipt acknowledges
installation. The existing full review retains the Method while matching native
job identities still hold pawn/target claims, including after partial completion.
Missing pawn rows or same-tick evidence preserve those claims. A later native observation
of completed, cancelled or replaced jobs releases their claims; retirement ends
the attempt when none remain. This neither credits predicted output nor proves
the owning Need met. New-work and cancellation policy remain separate from that
observed physical lifetime.

A Method owns an attempt at an observed outcome. Applied intent proves the write,
not the Concern's completion. Each family keeps its identity, memory and release
path. The common contract is a set of transitions, not another workflow engine
or persistent Method store.

A revision conflict while recording an acquisition cooldown aborts the current
step. The scheduler's existing failure path refreshes and replans; the planner
cannot continue selecting or withdrawing against stale owner and claim state.

| Evidence | Required decision |
| --- | --- |
| Stable prerequisites and useful issued work | Continue without replacing commands. |
| Required observations unknown | Hold useful work; neither infer completion nor admit its replacement. |
| Known danger, refusal or lost prerequisite | Reconsider. Unknown unrelated facts cannot erase known invalidation. |
| A newly available useful alternative | Reconsider; replace only when shared forecast comparison establishes the alternative. |
| Game-tick progress horizon reached | Reobserve and reassess; never cancel or certify completion solely from elapsed ticks. |
| Expected result observed | Release this responsibility; independently inspect the Concern's complete outcome. |

## Pawn activity Methods

The existing worker revisits installed single-batch Standard Methods independently
of new-work Concern eligibility. It reads exact pawn assignment/Method/revision
ownership. Missing pawn rows or an unknown Concern finding retain uncertainty.
Selected activity tasks and prerequisite edges live in that Method's existing
action payload. Each completed participant may advance independently; useful
running participants remain identical at the same revision. Preparing participants
may approach before prerequisites complete and wait for a fresh exact binding.
Food and construction use this one lifecycle, including observed output/carried
rebinding and bounded non-consuming retries. Consuming failure releases instead
of replaying. Future output IDs are never pre-authorized.
Stable needed work is left alone. A known recovered Concern, failed assignment
or expired final deadline produces an explicit release through the existing
journal and Hands. Different/newer native ownership is never released on behalf
of the old Method. Positive absence resolves the old obligation without a write.

`ContinueActivityMethod` replaces the Method's current plan atomically, retaining
the old plan as superseded history and keeping the Method identity. It refuses
unresolved installation receipts, stale world/load/generation or ticks, running
productive steps, changed assignment identities and omitted still-owned pawns.
Productive continuation requires an unmet Concern and its usual review/Safeguards.
A recovered Concern permits only release. The release authorization exception is
limited to plans with a recorded predecessor; it does not admit unrelated work.
Review cancellation preserves these cleanup plans until Hands resolves them.

Callers must bind productive steps to fresh observed targets/ingredients before
submission. The [harvest/delivery caller](pawn-activities.md#live-harvest-and-delivery)
binds observed loose food and retries interrupted, empty-handed delivery within
the original deadline/attempt budget. It releases carried-food attempts instead
of assuming the source still exists. A positively refused replacement retains
its installed predecessor's cleanup obligation; unknown receipts remain unknown.
The same caller can select one cooking iteration after observed harvest, supply
its bench, rebind the exact recipe to fresh ingredients, then deliver observed
meals. Failed supply or cooking releases rather than replaying consumption.
The normal coupled portfolio supplies these selected tasks. Carried ingredients
remain bounded by the exact native adapter; see [cooking limits](pawn-activities.md#live-one-iteration-cooking).

Productive alternatives for this caller are transient Method proposals: family
generation supplies forecast outcomes and exact target bindings, ColonyForecast's
shared outcome comparator chooses among them, and binding constructs the proposed
revision. No separate selection engine or Method lifecycle is created. The
[stage contract](../architecture/colony-forecast.md#live-activity-policy-stages)
defines the enforced boundary and current local valuation limits.

Native release retains the last release in the existing transient assignment row
for idempotent receipt retry, but reports no ownership and intercepts no jobs.
Fresh acquisition starts from expected revision zero. A stale release cannot
erase a subsequent assignment. World/authority changes clear this transient row.
Journal/policy tests cover lifecycle decisions and transactional continuation;
the prepared pawn lifecycle case checks repeated release and reacquisition.

## Combat shelter

Entry requires live threats and no viable combat assignment. Shelter selects
native-verified layout retreat cells first, then safe roofed rooms, then bounded
standable candidates away from threats on the defended side. Refused unreachable
cells remain excluded by the fight's existing memory. Missing geometry cannot
create a destination or invalidate useful previously issued shelter.

Arrival at a safe cell is useful while threats remain. An arrived pawn within a
hostile's observed weapon range (or adjacent melee reach), a refused destination,
a raid phase change or breach causes reassessment. Newly eligible defenders go
through the ordinary formation selector. Stable moving pawns receive no
replacement; unknown positions do not trigger movement. The existing humanoid
raid wait horizon is 38,000 game ticks; reaching it reassesses the fight without
proving the raid ended. Fight closure and roster undrafting retain their owners.

Reconsideration uses stable `defenders_available`, `shelter_exposed` and
`shelter_unreachable` reasons in existing `admission` rows.

## Disaster recovery

Entry requires a current disaster deficit or independently observed exposure
restriction. Pending actions remain owned by the shared Plan. After application,
the current pawn job and target establish whether repair, breakdown or refuel
work still serves an observed pending need. Increasing hit points or fuel does
not justify replacing that useful job. Unknown jobs or targets hold admission.
When the job ends, selection can reconsider known work using the shared Episode's
used Method identities; refusal does not erase that history. (Episodes are legacy;
see the [target model](../architecture/control-loop.md#target-model-needs-families-and-claimed-methods).)

The scheduler's existing game-tick review deadline releases its wait and obtains
fresh observations; it does not cancel the native job. Native building state and
service gates establish recovery. Neither an applied receipt nor an expired
condition duration establishes restoration. Known recovery releases the
Incident; independently observed hazard absence releases area restrictions.

Existing `planner_step` rows distinguish unknown observations, no eligible
worker, missing/protected infrastructure, existing work, exhausted methods and
no pending work. Existing log readers consume these rows.

## Evidence

The stable/reconstruction, unknown, deadline and
observed-outcome requirements apply to both owners: shelter (refused/wall
destinations, available defenders, exposed arrival) and recovery (job
progress, interruption, observed repair) decide from native
facts. Movement, path legality and completed repair remain native nightly
evidence. Extend a shared implementation to development only when it removes
duplicated decisions rather than renaming family branches.

## Selected clothing recipe continuation

Ordinary tailoring uses the same selected task graph and participant release as
food and construction. Exact recipe/stuff/input choice lives only in the admitted
Method action. Recipe completion enables output observation, never inventory
credit; delivery binds product definition **and selected stuff**. Changed stacks
may rebind only a not-yet-executed obligation with the same selected recipe,
stuff and total quantity. A failed consuming recipe is released rather than
replayed. Normal equipment review can then choose observed unfinished work as a
new Method, carrying its native remaining work and no fresh loose-input charge.

The native UFT and its bound bill preserve actual partial work across that
release. Hands cleans up only its own provisioned bill when no UFT exists; it
never removes a user bill or unsuspends an orphan after failure. Concern recovery
still does not erase participant release or observed-output obligations. See
[exact tailoring execution](pawn-activities.md#exact-tailoring-recipes).

A finished participant releases in a separate revision before another participant
binds new productive work. Retained orders and selected obligations stay exact;
the cleanup delta removes only the released participant's tasks and their
satisfied prerequisite edges. Store validates that no labor, target or input is
added before bypassing productive readmission for this cleanup-only delta.
A temporarily claimed output stack therefore cannot strand a completed
participant. Productive rebinding still requires ordinary shared admission,
fresh native evidence and the original finite deadline; cleanup grants no right
to take another Method's target.

An existing exact Method does not start or hold a later ordinary service.
At a task boundary, food/rest/recreation service returns that participant to
vanilla through exact owner cleanup. Missing access, an unread needs census or
blocked service supplies no authority to continue an old hypothetical task.
Cleanup still requires the observed execution identity; missing execution
ownership cannot authorize a release. No service completion is credited.
Independent running participants keep identical orders. If another participant's
remaining work depends on the released participant, the coordinated attempt ends
through the existing exact-owner release path rather than treating an unobserved
service as a completed prerequisite. Running work reaches its next boundary first;
an unlisted Need still permits cleanup and native handback but starts no new work
or preparation. Missing participant evidence never authorizes cleanup. These lifecycle checks do
not certify intake or complete the general intervention-justification migration.

An urgent rest or food need never interrupts a running task. At the next boundary (a task
just ended, or the pawn is waiting to depart) a participant whose native need is at or below
its threshold is released through the same separate-revision cleanup, unless another
participant's remaining task depends on one of its remaining tasks. The pawn then serves the
need, and the Method resumes it afterward if the demand remains. Unknown need evidence never
releases. The native activity read supplies needs for the batch's own pawns for this check.

A later hypothetical meal does not exempt the pawn's earlier work from this
needs check. Ordinary service handback itself requires no predicted service
duration or departure threshold.

Expected productive resource contention returns a typed ResourcesUnavailable
admission result without replacing the installed Method or advancing its owner
revision. Worker continues the remaining Methods and ordinary dispatch/review,
so an unrelated unowned pawn can receive its bounded activity and existing
native work can finish. Fresh observations retry through that same path; no
claim is relaxed. Stale identity, ownership, revision and other invariant failures
still throw. The existing coupled_observed signal reports deferred admission
after the result, rather than describing a rejected proposal as a transition.

Required zone refreshes, station role facts, defense geometry and work coverage
must succeed before a planning pass continues. A missing fact or broken invariant
ends that pass and reaches the scheduler's existing refresh/replan owner; earlier
coverage is never substituted. An open defense site has an empty rock list, while
an invalid opening fails. Containment may select shared material for future
acquisition when no allowed material is stocked, but missing stuff facts fail.
Unavailable optional clock status is absent in the returned step and is read
again on the next step; other status failures propagate.

Native authority generation rollover ends PawnActivities ownership. The current
shared action census excludes both pending and installed activity intent from
older generations, including predecessor cleanup history. It issues no release
against the new authority and grants no inventory credit: current native stock
still determines availability. Building and standing-bill commitments survive
authority changes and retain their existing accounting.

A selected future sleep or recreation service reserves its native target for
the whole Method, including Approach/Hold preparation. The shared claim census
feeds both candidate filtering and admission; another pawn cannot propose the
same bed or recreation object while only its destination cell appears occupied.
An exact observed-food service reserves only the units the Method's remaining
Eat tasks owe (#3194): a bite the continuation dropped as completed no longer
counts, the observed stack count less the owed units stays proposable and
admissible for another Method, and the owed count is never reduced by predicted
consumption. Native binds the later bite only to the observed lot holding at
least the owed count, so a stack that shrank, split, merged or moved below it
releases instead of binding a short count. Symbolic produced-food targets remain
unresolved and continue to use the existing physical input frontier until native
output rebinding.
